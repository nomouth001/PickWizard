## 1. 백테스트 중간 중단 방법

### 1.1 현재 구조

| 항목 | 내용 |
|------|------|
| **실행 방식** | `POST /backtest/run`(동기), `POST /backtest/run-stream`(NDJSON 스트리밍) |
| **스트리밍 시** | `run_sync()`를 `run_in_executor(None, run_sync)`로 스레드 풀에서 실행. 결과/진행은 `asyncio.Queue`로 스트리밍. |
| **취소 API** | 없음. 실행 중인 백테스트를 식별·취소하는 API 없음. |
| **루프** | `execute_walk_forward()` 내부 `for _, row in draws_in_range.iterrows()` — 매 회차마다 `generate_numbers()` 호출. 취소 플래그/이벤트를 보지 않음. |

- **run-stream**에서 클라이언트가 브라우저를 닫거나 연결을 끊어도:  
  `StreamingResponse`의 `generate()`는 끊김으로 종료되지만, **이미 스레드 풀에 넘긴 `run_sync()`는 그대로 끝까지 실행**됩니다.  
  즉, “연결 끊김 = 중단”이 되지 않음.

### 1.2 중단이 가능하도록 하려면 (구현 시 고려 방향)

1. **취소 플래그를 루프 안에서 보기**  
   - `execute_walk_forward(..., cancel_token=None)` 또는 `cancel_event: threading.Event` 같은 인자를 추가.  
   - 매 회차 시작 시(또는 `progress_callback` 호출 전) `cancel_token.is_cancelled()` / `cancel_event.is_set()` 체크 후 `break` 또는 조기 return.  
   - 스트리밍/비스트리밍 모두, “취소 요청이 있으면 다음 회차로 넘어가지 않고 종료”하려면 이 방식이 필요.

2. **스트리밍 시 “연결 끊김 → 취소” 반영**  
   - `run_stream`에서 `run_sync()`를 실행할 때, 위 취소용 `Event`를 함께 넘기고, **클라이언트 연결 끊김**을 감지하는 쪽에서 `event.set()` 호출.  
   - FastAPI/Starlette에서는 `Request`가 끊겼는지 주기적으로 확인하거나, `generate()`에서 `yield` 후 `request.is_disconnected`(또는 해당 프레임워크의 disconnect 감지)를 보고 끊기면 `event.set()`.  
   - 실행 쪽은 동기 함수이므로, **반드시 루프 내부에서 주기적으로 그 Event를 보는 코드**가 있어야 실제로 멈춤.

3. **별도 “취소” API**  
   - 백테스트 시작 시 `backtest_id` 또는 `run_id`를 발급해, 그 ID로 실행 중인 작업을 등록.  
   - `POST /backtest/cancel` 또는 `POST /api/admin/backtest/cancel` 에서 해당 ID에 대해 위와 같은 `cancel_event.set()` (또는 취소 플래그 설정) 수행.  
   - 실제 중단은 (1)과 동일하게, `execute_walk_forward` 루프 안에서 그 플래그/이벤트를 보고 break 하는 방식으로 구현.

4. **현재 가능한 “중단” (코드 수정 없이)**  
   - **브라우저 탭/창 닫기**: 스트리밍 응답만 끝날 뿐, 서버 쪽 백테스트는 계속 돌아감.  
   - **서버 프로세스 재시작**: 해당 프로세스가 죽으므로 당연히 중단됨.  
   - **타임아웃**: 리버스 프록시/로드밸런서에서 긴 요청 타임아웃을 두면, 그 시간 후 연결이 끊기지만, 역시 서버 쪽 `run_sync()`는 계속 실행될 수 있음.

**요약**: 지금 구조에서는 **의도적으로 “중간에 멈추는” 방법이 없음**. 중단을 지원하려면 “취소용 플래그/이벤트 + 루프 내 주기적 체크”가 필요하고, 선택적으로 연결 끊김 감지·취소 API를 붙이면 됨.

## 2. LSTM 백테스트가 오래 걸리는 이유

- **회차마다** `algorithm.generate_numbers(historical_data=hist, ...)` 가 호출됨.  
- **알고리즘 3(LSTM)** 은 **한 백테스트 실행에서 둘 중 하나만** 사용함 (`learning_mode` 파라미터 기준).  
  - **Non-cumulative**(기본값): 매 회차마다 `effective_window_size` 구간으로 **전체 학습** (create_sequences → train_lstm) 후 예측.  
  - **Cumulative**: (가능하면) 이전 회차까지 저장된 모델 로드 → **증분 데이터로 추가 학습** → 예측 → 모델 저장.  
- **참고**: Admin 백테스트 UI에는 LSTM의 누적/비누적 선택지가 없어, 현재는 **기본값(non-cumulative)** 으로만 실행됨. cumulative로 돌리려면 API 호출 시 `algorithm_params: { "learning_mode": "cumulative" }` 를 넘기거나, Admin UI에 “학습 방식” 선택을 추가해야 함.
- 따라서 “회차 수 × (학습 + 예측)” 만큼 연산이 **순차**로 쌓이고, 회차가 수백 개면 시간이 크게 늘어남.

## 3. 여러 회차를 병렬로 실행할 수 있는지

### 3.1 Walk-Forward의 순서 의존성

- 회차 **N** 에서 쓰는 `hist`는 **1 ~ (N-1) 회** 데이터.  
- 회차 N+1은 1~N 회 데이터가 필요하므로, **N+1의 입력은 N의 결과/상태에 의존하지 않지만**, “데이터 구간”이 순차적으로 늘어남.  
- 따라서 **같은 회차 N** 에 대해 “여러 번 생성”을 병렬로 돌리는 것은 의미 있지만, **서로 다른 회차**를 “완전 독립적으로” 병렬 돌리려면 주의가 필요함.

### 3.2 병렬화 가능 방향

| 방향 | 설명 | 장단점 |
|------|------|--------|
| **1) 회차 구간 분할** | 회차 범위를 여러 구간으로 나누어(예: 1–250, 251–500, 501–750, 751–1000) **각 구간만** Walk-Forward. 각 워커는 동일한 전체 DataFrame을 받고, 자신의 `start_draw`~`end_draw`만 반복. 회차 N에서 쓰는 `hist`는 여전히 1~(N-1)이므로, 구간 내에서는 기존과 동일한 시뮬레이션. | **Non-cumulative LSTM**: 구간별로 완전 독립이라 병렬이 깔끔함. **Cumulative LSTM**: 회차마다 모델을 디스크에 저장·로드하므로, 워커가 나뉘면 “워커별로 다른 모델 파일/상태”가 됨. 구간 경계에서 모델을 넘기지 않으면 cumulative 의미가 달라짐. 구간을 나누면 “구간 내에서만” cumulative로 동작하게 설계해야 함. |
| **2) 알고리즘/조합별 병렬** | 서로 다른 `algorithm_id` 또는 서로 다른 파라미터 조합에 대해 **백테스트 자체**를 여러 개 동시 실행. (이미 compare는 여러 알고리즘을 **순차** 실행.) | 구현이 단순함. LSTM 한 개의 “한 번의 긴 백테스트”를 쪼개는 것은 아니지만, 여러 설정을 동시에 돌려서 체감 대기 시간을 줄일 수 있음. |
| **3) LSTM 경량화** | 회차마다 풀 학습 대신, 예를 들어 **N회차마다만** 재학습하고 그 사이 회차는 이전 모델로만 예측. 또는 epoch/배치를 줄이기. | “완전 Walk-Forward”와는 시맨틱이 달라지지만, 동일 코드베이스에서 옵션으로 넣으면 실행 시간을 줄일 수 있음. |

### 3.3 정리

- **같은 회차를 여러 번** 병렬로 돌리는 것은 의미 없음(입력이 동일하고 결과만 여러 번 나옴).  
- **회차를 구간으로 나누어** 각 구간을 서로 다른 프로세스/스레드에서 Walk-Forward 하고, 마지막에 `rank_counts`·`detailed`·`total_sets` 등을 합치는 방식은 **가능**함.  
  - Non-cumulative LSTM이면 구간별로 완전 독립이라 병렬화 효과가 가장 분명함.  
  - Cumulative LSTM은 “모델 상태가 회차를 따라 감”이므로, 구간 분할 시 워커별 모델 경로/상태 정책을 정해야 함.  
- “여러 회차를 병렬로”라고 했을 때 **실무적으로 가장 현실적인 것**은 **회차 구간 분할 + 멀티프로세스(또는 멀티스레드 + 별도 모델 인스턴스)** 이고, 그 다음이 **알고리즘/파라미터별로 서로 다른 백테스트를 동시에 돌리기**임.
