# 048. 한국어/태국어 화면에서 스크롤 캡처 미동작 원인 조사 보고

**목적**: 한국어·태국어 UI일 때만 스크롤 캡처가 되지 않고, 다른 언어(영어·중국어·베트남어·일본어)에서는 되는 현상의 차이 요인 파악.  
**대상 화면**: **생성 번호 보는 화면(오프라인 결과 화면)** 만 해당. 다른 화면 아님.  
**코드 수정 없이** 원인 가능성만 정리.

---

## 0. 증상 정확한 기술

- **실제 증상**: 스크롤 캡처(롱 스크린샷) 실행 시 **화면은 스크롤을 한다**. 하지만 **캡처(저장되는 이미지)는 스크롤을 따라 확장하지 않는다**.
- 즉, 뷰는 스크롤되는데 **캡처가 한 장만 나오거나, 스크롤해도 아래 내용이 이어붙지 않는** 상태다. KO/TH에서만 이렇게 되고, 다른 언어에서는 스크롤하면 캡처도 같이 늘어난다.
- **검증 2번 결과**: 결과 화면 진입 후 **3~5초 기다렸다가** 스크롤 캡처를 해도 **동일하게 실패**한다. → “첫 프레임/폰트 준비 타이밍”으로 인한 일시적 실패 가설은 **약해짐**.

---

## 1. 문제가 나는 화면: 생성 번호(결과) 화면만 해당

- **오프라인 결과 화면** (`OfflineResultScreen`): 번호 생성 후 뜨는 화면.  
  상단에 알고리즘명·세트 수 카드 → **번호 공(NumberCard × N)** → 5세트 단위 복사 버튼들 → "내 번호로 저장" 버튼.
- 이 화면에서 **화면 대부분은 번호 공(LottoBall)** 이라, 언어를 바꿔도 **전체 스크롤 길이(콘텐츠 높이)가 언어별로 유의미하게 달라질 여지는 거의 없음**.
- 따라서 "한국어/태국어에서만 콘텐츠가 길어져서 스크롤 캡처가 실패한다"는 **가설은 이 화면에는 잘 맞지 않음**.

---

## 2. 결과 화면의 스크롤 구조 (공통)

- **body**: `ListView(padding: 16, children: [...])` — 고정 자식 리스트.
- 스크롤/레이아웃에 **로케일 분기 없음**. 모든 언어에서 동일 위젯 트리.

---

## 3. 결과 화면에서 로케일에 따라 바뀌는 부분 (텍스트만)

| 위치 | 내용 예 (KO / EN / TH) |
|------|------------------------|
| AppBar | 앱 이름 (럭키 찬스 645 / Lucky Chance 645 / ลักกี้ แชนซ์ 645) |
| 상단 카드 | 알고리즘명 + "N개 생성 완료" 등 (`algorithm1Name` / `algorithm9NameDisplay`, `setsGenerated`) |
| 각 번호 카드 | "세트 1" / "Set 1" / "ชุดที่ 1" (`setNumber`) |
| 복사 섹션 | "5세트 단위 복사" / "Copy in sets of 5" / "คัดลอกทีละ 5 ชุด" |
| 복사 버튼들 | "1~5세트 복사" / "Copy sets 1–5" 등 (`copySetsRangeButton`) |
| 저장 버튼 | "내 번호로 저장" / "Save as My Numbers" 등 |

→ **대부분은 번호 공 + 고정 레이아웃**이고, **텍스트는 짧은 라벨 몇 개**뿐이라, 언어가 바뀌어도 **전체 높이 차이는 작을 가능성이 큼**.

---

## 4. 한국어·태국어에서만 실패할 수 있는 다른 요인 (가설)

전체 길이 차이가 크지 않다면, 아래 같은 요인이 더 유력할 수 있음.

### 4.1 뷰포트/첫 프레임·스크립트 렌더링

- 스크롤 캡처가 **처음 보이는 영역(뷰포트)** 또는 **첫 스크롤 단위**를 기준으로 동작할 때,  
  그 안에 **한글/태국어**가 포함되면:
  - 레이어 구조가 로마자/한자와 다르게 그려지거나
  - 플랫폼/캡처 API가 "복잡 스크립트" 구간에서만 스크롤 뷰를 잘못 인식할 수 있음.
- 결과 화면에서는 **맨 위에** AppBar(앱 이름) + 알고리즘명·세트 수 **텍스트**가 오므로, **한국어/태국어일 때 그 영역의 렌더링 차이**가 캡처 실패와 연결될 여지가 있음.

### 4.2 플랫폼(OS/도구)의 스크립트별 처리

- OS 기본 롱 스크린샷/스크롤 캡처가 **텍스트 레이어나 접근성 트리**를 이용한다면,  
  한글/태국어만 다른 노드 구조나 바운드가 나와서 **스크롤 가능 영역을 잘못 계산**하거나, **캡처 대상을 놓칠** 수 있음.
- "다른 언어는 되고 KO/TH만 안 된다"는 점은 **콘텐츠 길이**보다 **화면에 보이는 스크립트(한글/태국어)** 와의 상관이 더 클 가능성을 시사함.

### 4.3 폰트 로딩·레이아웃 타이밍

- 한글/태국어 폰트가 **비동기 로드**되거나, 첫 프레임 이후에 치환되면,  
  캡처 시점에 **스크롤 뷰의 높이·스크롤 범위가 아직 확정되지 않았을** 수 있음.  
  그 경우 같은 결과 화면이라도 **로케일만 KO/TH일 때** 캡처가 실패하거나 잘못된 영역만 잡힐 수 있음.

### 4.4 레이어/RepaintBoundary

- Flutter가 **복잡 스크립트 텍스트**를 그릴 때 내부적으로 **다른 RepaintBoundary/레이어**를 쓰는 경우,  
  캡처 구현이 "스크롤 뷰의 자식"을 기대하는 구조와 맞지 않아 **KO/TH에서만** 실패할 수 있음.

## 5. 코드 상에서 확인된 점 (결과 화면 기준)

| 항목 | 내용 |
|------|------|
| 스크롤 위젯 | `ListView` + 고정 children (번호 카드 수만 데이터 의존) |
| 로케일 분기 | 스크롤/레이아웃 분기 없음 |
| 화면 대부분 | 번호 공(`LottoBall` size 44) + 카드 구조 → 언어와 무관 |
| 로케일 의존 | 짧은 라벨 텍스트 몇 곳뿐 (앱명, 알고리즘명, 세트 문구, 버튼 문구) |

→ **"생성 번호 보는 화면"에서는 전체 높이 차이보다, 상단 등에 있는 한글/태국어 텍스트의 렌더링·플랫폼 처리 차이가 원인일 가능성이 더 큼.**

---

## 6. 정리 및 추천 확인 사항

- **대상**: 스크롤 캡처 문제는 **생성 번호(결과) 화면**에서만 다룸.
- **높이 가설은 약함**: 이 화면은 대부분 번호 공이라, 언어별로 **전체 스크롤 길이가 유의미하게 다를 가능성은 낮음**.
- **유력한 방향**:
  - 결과 화면 **상단(AppBar·알고리즘 카드)** 에 나오는 **한글/태국어 텍스트**가 뷰포트·레이어·폰트 타이밍 측면에서 캡처와 상호작용하는지.
  - 사용 중인 스크롤 캡처가 **OS 기본 기능**인지 **앱/패키지**인지 확인 후, 해당 구현이 **특정 스크립트(한글/태국어)** 에서만 다르게 동작하는지 검색·재현.

## 7. 원인 좁히기 (추적 결과)

아래는 공개 자료·엔진 동작을 기준으로 가설을 더 좁힌 결과다.

### 7.1 Android 스크롤 캡처와 Flutter

- Android 12(API 31)부터 **ScrollCapture API**가 있으며, 앱은 **ScrollCaptureCallback**으로 스크롤 가능 영역과 타일 이미지를 제공한다.
- Flutter는 **2022년경**(이슈 #85978, PR #100800) Android 스크롤 캡처 지원을 추가했다. 즉, Flutter 앱도 시스템이 “스크롤 캡처”를 요청하면 **콜백을 통해 스크롤·타일 캡처**에 참여한다.
- Flutter는 **오프스크린 위젯을 기본적으로 그리지 않는다**. 따라서 스크롤 캡처 시에는 “스크롤 위치를 바꾼 뒤 해당 영역을 그려서 타일로 넘긴다”는 식의 **타일 단위 캡처**일 가능성이 크다.
- 정리하면, **언어와 무관하게 같은 ListView·같은 콜백**이 호출되며, 차이는 **“어떤 로케일일 때 그려서 넘기는 타일 이미지”** 쪽에서 날 가능성이 높다.

### 7.2 증상 재해석: “화면은 스크롤, 캡처는 확장 안 함”

- 사용자 확인: 스크롤 캡처 시 **화면(뷰)은 스크롤**되지만, **캡처(저장되는 롱 스크린샷)는 스크롤을 따라 늘어나지 않음** — 한 장만 나오거나 이어붙이기가 되지 않음.
- **검증 2번 수행 결과**: 결과 화면 진입 후 **3~5초 기다렸다가** 스크롤 캡처를 해도 **동일하게 실패**.  
  → “첫 프레임/폰트 준비가 늦어서 한 타일만 무효”라는 **타이밍 가설은 약해짐**. 대기로는 해소되지 않음.

### 7.3 유력한 원인(수정): 타일이 KO/TH일 때 “확장 중단”으로 처리됨

- 스크롤 캡처 흐름은 대략: 시스템이 스크롤 가능 영역을 스크롤시키고, **각 위치마다 타일 이미지를 요청**해 이어붙인다. 화면이 스크롤된다는 것은 **스크롤 자체는 인식·실행**되고 있다는 뜻이다.
- 그런데 **캡처가 확장되지 않는다**는 것은, **타일을 받은 쪽(OS/OEM 또는 Flutter 콜백 응답)에서 “이어붙이기를 하지 않기”로 결정**하고 있을 가능성이 크다. 예:
  - **첫 타일(또는 일부 타일)** 이 한글/태국어가 그려진 비트맵인 경우, OEM/시스템이 그 타일을 **유효하지 않다**고 판단해(예: 내용 검사, 포맷/크기 검증 실패) **이후 타일 요청을 하지 않거나**, 받아도 **스티칭하지 않음**.
  - 또는 Flutter의 ScrollCapture 콜백이 **KO/TH가 보이는 뷰 상태**에서 타일을 넘길 때 **형식·바운드·타이밍**이 달라져, 시스템이 “같은 스크롤 영역이 아니다”로 인식하고 확장을 멈춤.
- **타이밍**이 아니라 **“한글/태국어가 포함된 타일”에 대한 시스템/Flutter 쪽의 처리 차이**로 인해, **스크롤은 되지만 캡처 확장만 KO/TH에서 중단**되는 것으로 보는 것이 현재 증상과 더 잘 맞음.

### 7.4 차순위: 기기·OEM별 동작 차이

- 스크롤 캡처는 **OEM(삼성, 샤오미 등)** 이 자체 구현한 경우가 많고, “스크롤 가능 뷰 탐색”·“타일 유효성 판정” 방식이 제조사·Android 버전마다 다를 수 있다.
- Flutter는 **단일 Surface에 그리기** 때문에, OEM이 “네이티브 스크롤 뷰”를 기대하는 방식이면, **콘텐츠가 한글/태국어일 때만** 뷰 구조·레이어를 다르게 해석해 **캡처를 비활성화하거나 실패**시킬 여지가 있다.
- **확인 방법**: **다른 제조사·순정 Android** 기기에서 같은 앱·같은 결과 화면으로 KO/TH 스크롤 캡처를 시도해 보면, “특정 OEM + KO/TH” 조합에서만 나는지 좁힐 수 있다.

### 7.5 정리 (원인 좁힌 결과)

| 우선순위 | 추정 원인 | 근거 |
|----------|-----------|------|
| 1 | **KO/TH가 그려진 타일이 "유효하지 않음"으로 처리되어 캡처 확장 중단** |  화면은 스크롤되나 캡처는 확장되지 않음. 3~5초 대기 후에도 동일. 타이밍보다는 한글/태국어 포함 타일에 대한 OEM/시스템 또는 Flutter 콜백 응답 차이로 이어붙이기를 하지 않는 쪽이 유력 “첫 타일만 무효”로  |
| 2 | **OEM(기기)별 스크롤 캡처 구현 차이** | 특정 기기에서만 KO/TH일 때 실패할 수 있음. 다른 기기·순정에서 재현 여부로 구분 가능. |
| 3 | (과거 가설) 타일 캡처 시점·첫 프레임 타이밍 | 검증 2번으로 대기 후에도 실패해 **약해짐**. |

**추천 검증 절차 (원인 더 좁히기)**  
1. **기기 변경**: 동일 앱·KO/TH 결과 화면으로 **다른 제조사 또는 순정 Android** 에서 스크롤 캡처 시도 → 실패가 “특정 기기/OEM”에 한정되는지 확인.  
2. **캡처 시점**: 스크롤 캡처를 **결과 화면 진입 직후**가 아니라 **몇 초 기다린 뒤** 시도해 보기 → 텍스트·폰트가 완전히 준비된 뒤에는 성공하는지 확인 (타이밍 가설 검증).  
3. **Flutter/엔진 이슈 검색**: “Flutter Android scroll capture” + “complex script” / “Hangul” / “Thai” / “first frame” 등으로 이슈 검색해, 알려진 버그나 패치가 있는지 확인.

## 8. 검증 2번 수행: 캡처 시점 테스트 절차

**목적**: “결과 화면 진입 후 몇 초 기다렸다가 스크롤 캡처” 시에도 KO/TH에서 실패하는지 확인해, **타이밍(첫 프레임 미렌더)** 가설을 검증한다.

**준비**: 동일 기기·동일 앱에서, 생성 번호(결과) 화면이 나오는 플로우까지 진행 가능한 상태.

**절차**  
1. 앱 언어를 **한국어**로 설정한 뒤, 번호 생성까지 진행해 **생성 번호(결과) 화면**으로 이동한다.  
2. **A) 직후 캡처**: 결과 화면이 뜬 **즉시**(0초) 기기 기본 스크롤 캡처(롱 스크린샷 등)를 시도한다. → 성공/실패를 기록.  
3. **B) 대기 후 캡처**: 결과 화면에서 **아무 동작 없이 3~5초** 기다린 뒤, 같은 방식으로 스크롤 캡처를 시도한다. → 성공/실패를 기록.  
4. 앱 언어를 **태국어**로 바꾼 뒤, 같은 절차(1~3)를 반복한다. (결과 화면 진입 → 직후 캡처 vs 3~5초 후 캡처)  
5. **(선택)** 동일 조건으로 **영어** 등 정상 동작하는 언어에서도 “직후” vs “3~5초 후” 각 1회씩 시도해, 대기 여부에 따른 차이가 있는지 비교한다.

**검증 2번 수행 결과**
- **3~5초 대기 후** 스크롤 캡처를 시도해도 **KO/TH에서 동일하게 실패**함.
- 증상: **화면은 스크롤되지만, 캡처(롱 스크린샷)는 스크롤을 따라 확장하지 않음** — 한 장만 나오거나 이어붙이기가 되지 않음.

**해석**
- 대기 후에도 실패하므로 **타이밍(첫 프레임/폰트 준비 지연)** 가설은 **약해짐**.
- **스크롤은 되는데 캡처만 확장되지 않는** 점을 고려하면, **타일 이미지가 KO/TH일 때 시스템 또는 Flutter 쪽에서 "유효하지 않다"고 판단해 이어붙이기를 하지 않는** 방향으로 원인을 좁히는 것이 타당함(섹션 7.3 참고).

## 9. 검증 3번 수행: Flutter/엔진 이슈 검색 결과

**검색 쿼리**: `Flutter Android scroll capture`, `Flutter scroll capture complex script`, `Flutter scroll capture Hangul Korean`, `Flutter scroll capture Thai`, `Flutter scroll capture first frame` 및 관련 조합.

**결과 요약**

| 검색 포인트 | 결과 |
|-------------|------|
| **Scroll capture + 한국어/태국어/복잡 스크립트** | Flutter 공식 이슈에서 **“스크롤 캡처가 KO/TH 또는 complex script에서만 실패한다”** 고 명시한 이슈는 **찾지 못함**. |
| **Flutter Android 스크롤 캡처 지원** | [#85978](https://github.com/flutter/flutter/issues/85978)에서 2022년 경 지원 추가·완료(Closed). OnePlus 9 Pro 등에서 동작 확인된 사례 있음. |
| **한글 텍스트 렌더링** | 스크롤 캡처와 직접 연관된 이슈는 없음. 한글 관련으로는 **Text 줄바꿈 오류**(#62331919), **다국어 텍스트 여백/스타일 차이**(#71620327), **웹 Multiline TextField 한글 입력 문제**(#134797) 등이 있음. → 복잡 스크립트가 레이아웃/프레임에 차이를 만드는 사례는 있으나, scroll capture 전용 보고는 없음. |
| **스크린샷·캡처 기기별 이슈** | [#163423](https://github.com/flutter/flutter/issues/163423): Android 특정 기기(Tecno BE8, Samsung A04 등)에서 **RenderRepaintBoundary/toImage() 결과가 세로로 뒤집혀 나오는** 문제 보고. GPU/렌더링 경로 차이로 추정. **언어/로케일과는 무관**하며, 스크롤 캡처와 동일한 캡처 경로를 쓸 경우 같은 기기에서 영향 받을 수 있음. |
| **통합 테스트 스크린샷** | Android에서 `convertFlutterSurfaceToImage()` 전에 **`pumpAndSettle()`** 를 한 번 더 호출하면 hang을 줄일 수 있다는 사례 있음(Stack Overflow). → **프레임 준비(레이아웃 안정화) 후 캡처**가 중요하다는 정황과 맞음. |

**정리**  
- **“스크롤 캡처 + 한국어/태국어”** 조합의 알려진 Flutter/엔진 버그는 **없음**.  
- 다만 (1) 한글 등 복잡 스크립트의 렌더링/레이아웃 이슈, (2) 특정 Android 기기의 캡처 결과 뒤집힘, (3) 캡처 전 프레임 안정화(`pumpAndSettle`) 필요 사례는 존재하므로, **타이밍·기기별 요인**을 검증 2번·1번으로 계속 좁히는 것이 좋다.

## 10. 해결을 위한 코드 수정 제안 (KO/TH일 때 타일이 "유효하지 않다"고 판단되어 이어붙이기가 되지 않는 경우)

아래는 **코드를 실제로 수정하지 않고**, 해결 방향을 보고서에만 정리한 제안이다. 적용 시에는 우선순위·구현 난이도·사이드 이펙트를 고려해 선택하면 된다.

### 10.1 앱 내 스크롤 캡처 기능 추가 (권장·우회)

**목적**: OS/OEM의 롱 스크린샷에 의존하지 않고, 앱 안에서 **전체 스크롤 영역을 한 번에 캡처**해 저장·공유하게 한다.

**제안 내용**  
- 결과 화면(생성 번호 보는 화면)에 **"전체 화면 캡처"** 또는 **"스크롤 캡처"** 버튼을 둔다.  
- 해당 버튼 탭 시 **Flutter 패키지**를 사용해 `ListView` 전체 콘텐츠를 이미지로 렌더링한 뒤 파일로 저장하거나 공유 시트를 띄운다.  
- 사용 패키지 후보: `scroll_screenshot`, `flutter_long_screenshot`, `widget_screenshot_plus` 등 (각 패키지는 `RepaintBoundary` + 스크롤/렌더링으로 긴 이미지 생성).  
- 이렇게 하면 **언어와 무관하게** 앱이 직접 비트맵을 만들기 때문에, OEM이 "KO/TH 타일을 유효하지 않다"고 판단하는 문제를 **우회**할 수 있다.

**장점**: 원인(OS/OEM 타일 유효성 판정)을 수정하지 않아도, 사용자는 KO/TH에서도 긴 화면 캡처를 얻을 수 있음.  
**단점**: UI에 버튼이 하나 추가되고, 패키지 의존성·유지보수 부담이 생김.

### 10.2 폰트·텍스트 "웜업" (첫 타일 품질 개선 시도)

**목적**: 결과 화면에 진입했을 때 **한글/태국어 폰트와 텍스트 shaping이 이미 한 프레임이라도 그려진 상태**가 되도록 해, 스크롤 캡처가 첫 타일을 요청할 때 비트맵이 더 안정적으로 나가게 한다.

**제안 내용**  
- 결과 화면(`OfflineResultScreen`)의 `build` 직후 또는 `initState`/`didChangeDependencies`에서, **화면 밖 또는 크기 0**인 `Text` 위젯으로 현재 로케일의 대표 문자열(예: `context.l10n.appNameOffline`)을 한 번 포함시키거나,  
- 결과 화면 진입 시 **한 프레임 지연**(`WidgetsBinding.instance.addPostFrameCallback`) 후에만 본문을 보이게 하는 식으로, **첫 프레임에 복잡 스크립트가 확실히 커밋**되도록 한다.  
- 또는 앱 기동 시 또는 언어 전환 시, **미리 사용할 폰트가 로드**되도록(예: `FontLoader` 또는 해당 로케일 문구를 한 번 그리기) 하는 방식을 검토한다.

**전제**: "첫 타일이 비어 있거나 불완전해서 무효 처리된다"는 가설이 맞을 때만 효과가 있을 수 있음. 현재는 "대기 후에도 실패"하여 타이밍 가설이 약해진 상태이므로, **효과는 제한적일 수 있음**.  
**위험**: 불필요한 지연이나 레이아웃 플래시가 생기지 않도록, 지연 시간은 최소화하고 가능하면 0크기/오프스크린 웜업만 쓴다.

### 10.3 RepaintBoundary로 스크롤 영역 격리

**목적**: 스크롤 가능한 콘텐츠를 **별도 레이어(RepaintBoundary)** 로 감싸서, 캡처 파이프라인이 타일을 가져갈 때 레이어 구조가 로케일과 무관하게 동일해지도록 한다.

**제안 내용**  
- 결과 화면의 `ListView`(또는 그 직계 자식인 콘텐츠 `Column`/리스트)를 **`RepaintBoundary`** 로 한 번 감싼다.  
- 이때 `child`는 기존과 동일하게 두고, **레이어 경계만 추가**하는 수준으로 한다.  
- Flutter 엔진이 ScrollCapture 타일을 만들 때 이 경계를 기준으로 비트맵을 자르면, **복잡 스크립트가 다른 레이어에 섞여 나가는** 상황이 줄어들 수 있다는 가정이다.

**전제**: 원인이 "한글/태국어 텍스트가 다른 레이어에 그려져서 타일이 깨진다"일 때만 의미 있음. 현재는 추정 단계이므로 **실험적** 적용에 그친다.  
**위험**: RepaintBoundary가 과하면 메모리·성능에 악영향을 줄 수 있으므로, **한 겹만** 추가하는 것을 권장한다.

### 10.4 Flutter/엔진 쪽 이슈 제보 및 개선 요청

**목적**: "KO/TH가 보이는 뷰에서 Android ScrollCapture 타일이 확장되지 않는다"는 증상을 **Flutter 또는 Android 쪽 이슈**로 남기고, 장기적으로 플랫폼에서 수정되도록 한다.

**제안 내용**  
- **재현 절차**(앱 로케일 KO/TH, 결과 화면에서 OS 롱 스크린샷 실행, 화면은 스크롤되나 캡처는 확장 안 됨)와 **기기·OS 버전·Flutter 버전**을 정리한 뒤,  
- Flutter 저장소에 **새 이슈**를 올리거나, 기존 이슈(#85978 등)에 **댓글**로 "complex script(한글/태국어) 화면에서 캡처 확장이 되지 않는 기기가 있다"는 사례를 첨부한다.  
- 제목/본문에 **"scroll capture"**, **"ScrollCaptureCallback"**, **"Hangul"**, **"Thai"**, **"tile"**, **"capture does not extend"** 등 키워드를 넣어 검색되게 한다.  
- 코드 수정은 **우리 앱이 아니라** Flutter 엔진 또는 Android ScrollCapture 구현 쪽에서 이루어져야 하는 부분이므로, 여기서는 **제보·요청**만 정리한다.
